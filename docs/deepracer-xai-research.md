# Visual Explainability for AWS DeepRacer CNN/RL Models — Research Report

Context note: the target repo (`larsll/deepracer-viz`, forked from `jochem725/deepracer-viz`) loads frozen TF1 `.pb` graphs via `tf1.Session`/`graph_def` (not a Keras `Model` object) and implements classic Grad-CAM manually (`deepracer_viz/gradcam/cam.py`), averaging gradients over multiple conv layers for a single hardcoded output unit. This matters for library compatibility below.

## 1. CAM family beyond Grad-CAM

| Method | Paper/Repo (year) | Type | Compute | Small/low-res grayscale CNN fit | Discrete vs continuous | TF/Keras vs agnostic |
|---|---|---|---|---|---|---|
| **Grad-CAM** (baseline) | Selvaraju et al., [1610.02391](https://arxiv.org/abs/1610.02391) (2017) | Gradient | 1 fwd+bwd pass | Good | Discrete (pick logit) or continuous (pick mean output) | Raw TF ops (current impl) |
| **Grad-CAM++** | Chattopadhay et al., [1710.11063](https://arxiv.org/abs/1710.11063) (2017, WACV18) | Gradient (2nd/3rd-order) | ~1 fwd+bwd, extra elementwise ops | Good; better with multiple co-occurring objects — less relevant for single-lane steering but harmless | Both | Easy in raw TF (needs 2nd derivatives via `tf.gradients` twice, or Hessian-vector) |
| **XGrad-CAM** | Fu et al., [2008.02312](https://arxiv.org/abs/2008.02312) (2020, BMVC) | Gradient | Same cost as Grad-CAM | Good; axiomatic (conservation+sensitivity), more faithful | Both | Trivial to add to current graph (just reweight) |
| **Score-CAM** | Wang et al., [1910.01279](https://arxiv.org/abs/1910.01279) (2019/2020) | **Gradient-free** (perturbation via forward passes masking each channel) | N forward passes (N = #channels in target layer, e.g. 32–64 for DeepRacer) | Cheap per-pass since input is tiny (160×120 gray) — practical here despite being "slow" generally | Both (any scalar target score) | Pure forward passes — works with ANY framework incl. raw TF1 session (no gradient op needed) |
| **Ablation-CAM** | Desai & Ramaswamy, [WACV20 PDF](https://openaccess.thecvf.com/content_WACV_2020/papers/Desai_Ablation-CAM_Visual_Explanations_for_Deep_Convolutional_Network_via_Gradient-free_Localization_WACV_2020_paper.pdf) (2020) | Gradient-free (channel ablation) | N forward passes | Same as Score-CAM; good fit | Both | Forward-pass only, framework-agnostic |
| **Eigen-CAM** | Muhammad & Yeasin, [2008.00299](https://arxiv.org/abs/2008.00299) (2020) | **Gradient-free** (PCA of activations, no class score at all) | 1 forward pass + SVD on small matrix | Extremely cheap, trivial to implement for tiny feature maps; but **class-agnostic** — same map regardless of steering/speed action, so less useful for distinguishing actions | N/A (not class-specific) | Pure linear algebra, trivially framework-agnostic |
| **LayerCAM** | Jiang et al., [IEEE TIP 2021 PDF](http://mftp.mmcheng.net/Papers/21TIP_LayerCAM.pdf), [repo](https://github.com/PengtaoJiang/LayerCAM) | Gradient (element-wise, per-location weight) | ~Grad-CAM cost | Good for shallow nets — can fuse **early+late conv layers**, useful since DeepRacer's shallow CNN has only 3–5 conv layers | Both | Simple, implementable on raw TF graph |
| **HiResCAM** | Draelos & Carin, [2011.08891](https://arxiv.org/abs/2011.08891) (2020) | Gradient (element-wise mult. of grads×activations, no spatial averaging) | ~Grad-CAM cost | **Important**: proven *faithful* (only highlights locations that actually affected the score) vs Grad-CAM which the paper shows can highlight unused regions due to gradient-averaging; strongly recommended replacement for last-conv-layer explanations, esp. for single-object/road-scene framing | Both | Trivial drop-in replacement in current `cam.py` (remove the `np.mean(grads, axis=(0,1))` averaging step, multiply element-wise instead) |
| **FullGrad** | Srinivas & Fleuret, [1905.00780](https://arxiv.org/abs/1905.00780) (NeurIPS 2019) | Gradient (full-network, all layers + biases) | Needs gradient/bias terms from every layer | More complex plumbing for a raw-graph TF1 model but feasible; completeness property is attractive | Both | Needs access to all layer biases — harder with current minimal `Model` wrapper |
| **Smooth Grad-CAM++** | Omeiza et al., [1908.01224](https://arxiv.org/abs/1908.01224) (2019) | Gradient + noise averaging | ~20–50× Grad-CAM++ cost (SmoothGrad samples) | Fine given tiny input size | Both | Straightforward combination of existing building blocks |
| **Recipro-CAM** | Byun & Lee, [2209.14074](https://arxiv.org/abs/2209.14074) (2022) | **Gradient-free** (spatial masking of feature maps, reciprocal scoring) | ~148× faster than Score-CAM, near Grad-CAM speed | Very good fit — fast + gradient-free, ideal when exporting graph-level gradients is awkward (e.g. SAC continuous heads) | Both | Framework-agnostic (forward-pass masking) |
| **Opti-CAM** | Zhang et al., [2301.07002](https://arxiv.org/abs/2301.07002) (2023) | Hybrid (optimizes per-image weights of CAM linear combination via gradient descent on masked logit) | Iterative optimization per image (slower, interactive use only) | Possible but too slow for per-frame video overlay at scale | Both | Needs a differentiable wrapper; non-trivial on raw TF1 graph |
| **ShapleyCAM** | Cai, [2501.06261](https://arxiv.org/abs/2501.06261) (2025), [repo](https://github.com/caihuaiguang/pytorch-shapley-cam) | Gradient + Hessian (2nd-order Taylor approx. of Shapley value) | ~2× Grad-CAM (needs Hessian-vector product) | Theoretically grounds HiResCAM/Grad-CAM in game theory; good quality but added implementation complexity | Both | PyTorch reference impl; portable math, re-implementable in TF |
| **Finer-CAM** | Zhang et al., [2501.11309](https://arxiv.org/abs/2501.11309) (2025, CVPR), [repo](https://github.com/Imageomics/Finer-CAM) | Gradient (CAM + comparative logit vs. similar classes) | ~Grad-CAM cost | **Highly relevant for DeepRacer's discrete action space**: explicitly designed to separate "why action A and not very-similar action B" (e.g., steer 10° vs 15°) — exactly the fine-grained discrimination problem among DeepRacer's steering bins | Discrete (needs comparator classes); continuous variant would need adaptation | Compatible with any CAM backend, drop-in wrapper |

**Known issues flagged by the literature itself:**
- Grad-CAM's gradient-averaging step can highlight image regions the network never actually used for its decision — this is the central critique in the **HiResCAM paper** (arXiv:2011.08891), which proves HiResCAM is faithful while Grad-CAM is not guaranteed to be.
- **Sanity Checks for Saliency Maps** (Adebayo et al., [1810.03292](https://arxiv.org/abs/1810.03292), NeurIPS 2018) shows several popular saliency methods are insensitive to model/data randomization (edge-detector-like behavior) — a mandatory check before trusting any CAM variant on a DeepRacer model.
- A follow-up, **Revisiting Sanity Checks for Saliency Maps** ([2110.14297](https://arxiv.org/abs/2110.14297)), argues the original sanity-check conclusions can be confounded by task choice — worth being aware the debate isn't fully settled.

## 2. Pixel-attribution methods

| Method | Link (year) | Type | Fit for DeepRacer | Framework |
|---|---|---|---|---|
| Integrated Gradients | Sundararajan et al., [1703.01365](https://arxiv.org/abs/1703.01365) (2017) | Gradient (path integral vs. baseline) | Needs ~20–50 interpolation steps × fwd+bwd; cheap given tiny input; needs a sensible "black" baseline image | TF-native via `tf.gradients` in a loop; also in Captum/tf-keras-vis-adjacent tools |
| SmoothGrad | Smilkov et al., [1706.03825](https://arxiv.org/abs/1706.03825) (2017) | Gradient + noise | Cheap; good denoising for low-res grayscale (reduces pixel-level gradient noise) | Trivial on raw graph |
| Guided Backprop / Guided Grad-CAM | Springenberg et al. 2014 / Selvaraju et al. 2017 | Gradient (modified ReLU backward) | Combine with Grad-CAM for pixel-sharp maps; flagged as failing some sanity checks (Adebayo 2018) | Needs custom gradient override of ReLU op — doable in TF1 graph via `tf.RegisterGradient` |
| Expected Gradients | Erion et al., [1906.10670](https://arxiv.org/abs/1906.10670) (2019/2021, Nat. Mach. Intell.) | Gradient (IG variant with dataset-sampled baselines) | Good — avoids picking an arbitrary single baseline, useful since "black frame" isn't a natural baseline for driving scenes | TF-compatible |
| DeepLIFT | Shrikumar et al., [1704.02685](https://arxiv.org/abs/1704.02685) (2017) | Gradient-like (reference activation difference) | Needs per-layer reference propagation; more engineering on raw frozen graph | Supported in Captum (PyTorch) / iNNvestigate (Keras) — awkward for raw TF1 session |
| SHAP (GradientSHAP/DeepSHAP) | Lundberg & Lee, [1705.07874](https://arxiv.org/abs/1705.07874) (2017, NeurIPS) | Gradient/perturbation hybrid | GradientSHAP is IG+SmoothGrad hybrid, easy; DeepSHAP needs DeepLIFT-style backprop | `shap` library has TF/Keras GradientExplainer support |
| LRP | Bach et al. 2015 (PLOS ONE); surveyed via [Zennit](https://github.com/chr5tphr/zennit) | Rule-based backward propagation | Conceptually strong for conv nets; "LRP for RL" is not a mainstream distinct subfield but LRP has been applied to policy networks in interpretability case studies | Zennit/iNNvestigate are the reference implementations, both are PyTorch/Keras-centric — porting rules to raw TF1 graph is nontrivial |
| RISE | Petsiuk et al., [1806.07421](https://arxiv.org/abs/1806.07421) (2018) | **Perturbation, black-box** | Hundreds of random masks × forward pass — cheap per-pass at 160×120 but needs many passes (1000s) for stable maps; fully model-agnostic (works even if gradients are unavailable, e.g. exported SavedModel/TFLite) | Totally framework-agnostic |
| LIME | Ribeiro et al., [1602.04938](https://arxiv.org/abs/1602.04938) (2016) | Perturbation, black-box (superpixel segmentation + local linear surrogate) | Superpixel segmentation on 160×120 grayscale road scenes can be unstable/coarse; moderate compute (local surrogate fitting) | Framework-agnostic (`lime` package) |
| Occlusion | Zeiler & Fergus-style sliding window | Perturbation | Simple sliding gray/black patch — cheap at low-res, very interpretable, no gradients needed at all (works on the frozen `.pb` with pure `session.run`) | Fully agnostic — arguably the **easiest robust baseline** to add to this tool |
| Meaningful Perturbation / Extremal Perturbations | Fong & Vedaldi 2017; Fong et al., [1910.08485](https://arxiv.org/abs/1910.08485) (2019, ICCV, `TorchRay`) | Perturbation (optimized smooth mask) | Theoretically grounded, optimization-based — higher compute (iterative) but still fine on 160×120 | TorchRay is PyTorch-only; concept portable |

## 3. RL-specific saliency

- **Greydanus et al., "Visualizing and Understanding Atari Agents"**, [1711.00138](https://arxiv.org/abs/1711.00138) (ICML 2018), [code](https://github.com/greydanus/visualize_atari) — perturbation saliency using a Gaussian blur mask swept over the frame, measuring the KL-divergence/change in the policy or value output. Directly portable to DeepRacer: blur patches of the 160×120 frame and measure change in steering/speed distribution. Cheap (one forward pass per mask position), framework-agnostic, and arguably the most natural extension of the existing Grad-CAM tool toward *perturbation-based* (gradient-free) RL saliency.
- **SARFA** — Puri et al., "**Explain Your Move**: Understanding Agent Actions Using Specific and Relevant Feature Attribution", [1912.12191](https://arxiv.org/abs/1912.12191) (ICLR 2020), [project page](https://nikaashpuri.github.io/sarfa-saliency/). Perturbation-based but balances "specificity" (does perturbing this region change only the target action's relative reward) against "relevance" (does it leave other actions' rankings undisturbed) — produces much more focused maps than naive perturbation saliency. Good fit: works directly on a discrete action-value/probability vector, exactly DeepRacer's discrete PPO/SAC output format.
- **Value-function vs. policy saliency**: both Greydanus and SARFA support computing saliency w.r.t. the **value head** as well as the policy head — for DeepRacer this would mean separately visualizing "what influences predicted future reward" vs. "what influences the chosen steering/speed," which is a cheap, novel addition given the SAC/PPO value head is already part of the exported graph for some model variants.
- **Atrey, Clary & Jensen, "Exploratory Not Explanatory"**, [1912.05743](https://arxiv.org/abs/1912.05743) (ICLR 2020) — an important critique: empirically shows saliency-map-based claims about Atari agents are often unfalsifiable/subjective and proposes counterfactual testing instead. Directly relevant caveat for any DeepRacer saliency tool: treat Grad-CAM/SARFA overlays as *hypothesis generators*, not proof, and ideally pair with behavioral tests (e.g., does occluding the highlighted region actually change the car's chosen action on replay?).
- **Olson et al., "Counterfactual State Explanations for RL Agents via Generative Deep Learning"**, [2101.12446](https://arxiv.org/abs/2101.12446) (Artificial Intelligence J., 2021), [code](https://github.com/mattolson93/counterfactual-state-explanations) — generates minimally-edited counterfactual frames that would flip the agent's action, using a generative model (encoder-decoder/GAN). High implementation cost (needs training a generative model of track frames) but conceptually the strongest complement to saliency per Atrey et al.'s critique; a stretch goal rather than near-term addition.
- **Frost et al., "Explaining RL Policies through Counterfactual Trajectories"**, [2201.12462](https://arxiv.org/abs/2201.12462) (2022) and **Shi et al., "Counterfactual Shapley Values"**, [2408.02529](https://arxiv.org/abs/2408.02529) (2024) — more recent counterfactual/Shapley directions in XRL, relevant as background but overkill for a frame-level video overlay tool.
- **Temporal saliency across frame stacks**: not a single canonical citation, but both Greydanus and SARFA naturally extend to frame-stacked inputs by computing per-frame-channel saliency and comparing contribution across the stack — directly applicable to DeepRacer's stereo-camera/stacked-frame variants (visualize which of the N stacked/stereo channels drove the decision).
- **Saliency for SAC / continuous control**: perturbation methods (Greydanus-style, SARFA, RISE, occlusion) generalize trivially to continuous outputs by measuring change in the predicted mean/std rather than a softmax probability; gradient-based CAM methods for continuous heads should pick the mean-action output (or a specific scalar, e.g. steering mean) as the backprop target, analogous to picking a logit — no fundamental new method required.
- **XRL survey**: Milani, Topin, Veloso & Fang, "**A Survey of Explainable Reinforcement Learning**", [2202.08434](https://arxiv.org/abs/2202.08434) (2022) — comprehensive taxonomy of self-explainable vs. post-hoc, policy-level vs. model-level XRL methods; a good map of the broader space beyond saliency (reward decomposition, policy summarization/distillation, etc.) if later broadening the tool's scope.

## 4. Autonomous-driving-specific

- **VisualBackProp** — Bojarski et al., [1611.05418](https://arxiv.org/abs/1611.05418) (2016/2017) — a fast, gradient-free, layer-by-layer mask propagation method (multiply up-sampled deeper-layer activation masks back through shallower layers) developed explicitly as a **real-time debugging tool for end-to-end steering CNNs** (NVIDIA PilotNet). Very low compute (single forward pass, no backprop at all), explicitly validated to run faster than LRP while giving comparable results — arguably the best-suited *driving-specific* technique for a small CNN like DeepRacer's, and notably it requires **no gradient ops**, so it works even on an opaque/optimized frozen graph.
- **Bojarski et al., "Explaining How a Deep Neural Network Trained with End-to-End Learning Steers a Car"**, [1704.07911](https://arxiv.org/abs/1704.07911) (2017) — companion paper, uses VisualBackProp to show PilotNet attends to lane markings, road edges, and parked cars; direct precedent for DeepRacer's track-edge/line-following behavior analysis.
- **Kim & Canny, "Interpretable Learning for Self-Driving Cars by Visualizing Causal Attention"**, [1703.10631](https://arxiv.org/abs/1703.10631) (2017, ICCV) — trains a visual-attention model jointly with the steering predictor, then applies a **causal filtering step** (masking attended regions and testing whether the output actually changes) to separate true causal attention from spurious attention-map activation. The causal-filtering idea is directly reusable as a validity check layered on top of Grad-CAM/VisualBackProp outputs for DeepRacer, without needing to retrain the model with an attention branch.

## 5. Evaluation metrics for saliency faithfulness

- **Deletion/Insertion AUC** — introduced with RISE ([1806.07421](https://arxiv.org/abs/1806.07421)): progressively delete (or insert) pixels in order of saliency rank and plot the drop (or rise) in the target score; area-under-curve summarizes faithfulness. Cheap to compute given the tiny 160×120 input and a single forward pass per step.
- **ROAD (ReOve And Debias)** — Rong et al., "**A Consistent and Efficient Evaluation Strategy for Attribution Methods**", [2202.00449](https://arxiv.org/abs/2202.00449) (ICML 2022), [code](https://github.com/tleemann/road_evaluation). Shows naive deletion metrics leak information through the *shape* of the removed region (not just pixel values) and proposes a debiased imputation-based removal strategy that is also ~99% cheaper than retrain-based evaluation (no retraining needed) — a good practical replacement for naive deletion/insertion AUC.
- **Sanity Checks** — Adebayo et al., [1810.03292](https://arxiv.org/abs/1810.03292) (2018): randomize model weights (layer-by-layer) or labels and check the saliency map changes meaningfully; essential minimal check before trusting any new CAM variant added to the tool.
- **ADCC (Average Drop–Coherence–Complexity)** — Poppi et al., "**Revisiting the Evaluation of CAM for Explainability**", [2104.10252](https://arxiv.org/abs/2104.10252) (CVPR-W 2021): combines average-confidence-drop, map coherence, and complexity (sparsity) into one score; used as the benchmark metric in several recent CAM papers (Recipro-CAM, ShapleyCAM) cited above.
- **Average Drop % / Increase in Confidence** — originally defined in the Grad-CAM++ paper ([1710.11063](https://arxiv.org/abs/1710.11063)): mask image by the saliency map and measure drop (bad) or increase (good, indicates map over-restricts to very few confident pixels) in predicted score for the target class/action.
- **Quantus** — Hedström et al., "**Quantus: An Explainable AI Toolkit for Responsible Evaluation**", [2202.06861](https://arxiv.org/abs/2202.06861) (JMLR 2023), [repo](https://github.com/understandable-machine-intelligence-lab/Quantus) — a maintained Python library bundling faithfulness, robustness, localization, complexity, and randomization (sanity-check) metrics; framework-agnostic wrapper (works with any `model(x)->scores` callable, so it can wrap a raw TF1 `session.run`), making it a strong candidate to add systematic metric reporting to the DeepRacer tool without reimplementing each metric.

## 6. Non-saliency visualizations useful for DeepRacer

- **Feature-map / filter visualization**: dump intermediate conv activations directly (no attribution math needed) — trivial with the existing `Model.get_conv_outputs()` helper already in this repo; useful standalone diagnostic for "is this filter dead/saturated."
- **Activation maximization**: synthesize an input image that maximally activates a given conv filter or an output steering/speed logit (`tf-keras-vis`'s `ActivationMaximization`, originally from the "Feature Visualization" line, [distill.pub/2017/feature-visualization](https://distill.pub/2017/feature-visualization/)). Harder to make visually meaningful at 160×120 grayscale (track scenes, not natural-image statistics) but can reveal "what pattern most excites full-left-steer."
- **t-SNE / UMAP of penultimate-layer embeddings**, colored by chosen action or track position/segment — not XAI-paper-specific but a standard technique (e.g., as used in Greydanus et al.'s Atari work) extremely well suited to a recorded-lap tool: embed the pre-output dense layer activations per frame, color by steering bin or track sector, to reveal whether the policy clusters cleanly by "turn type."
- **Policy entropy / action-distribution over the track**: plot softmax entropy (discrete) or predicted std (continuous/SAC) per track position — a lightweight, code-only addition (no new ML dependency) that complements saliency by showing *where* the agent is confident vs. uncertain.
- **Value-function heatmaps over track position**: if the exported graph retains the critic/value head (common in PPO/SAC training graphs before export-time pruning), plot predicted value along the recorded trajectory — directly analogous to the "value saliency" distinction in Greydanus et al. and SARFA.
- **TCAV (Testing with Concept Activation Vectors)** — Kim et al. 2017 (original, pre-arXiv widely cited; robustness follow-up: Soni et al. [2002.03549](https://arxiv.org/abs/2002.03549)). Requires hand-labeled concept example sets (e.g., "left-curve," "center-line-visible," "off-track") — feasible for DeepRacer given recorded laps can be sliced into concept buckets by track geometry, but needs manual curation effort.
- **CRAFT (Concept Recursive Activation FacTorization)** — Fel et al., [2211.10154](https://arxiv.org/abs/2211.10154) (CVPR 2023), [repo](https://github.com/deel-ai/Craft) — automatic (unsupervised) concept discovery + concept attribution maps, avoids TCAV's manual-labeling requirement; implemented in the TF-native Xplique library (see below), a good match for this TF-based tool.
- **CRP (Concept Relevance Propagation)** — Achtibat et al., [2206.03208](https://arxiv.org/abs/2206.03208) (Nature Machine Intelligence, 2023) — combines LRP-style attribution with concept-level "what" + "where" explanations and concept atlases; powerful but implementation (Zennit-based) targets PyTorch and assumes deeper networks than DeepRacer's 3–5 conv layers — likely more machinery than needed here.
- **Mechanistic-interpretability basics**: for a network this small (3–5 conv layers, few hundred-thousand parameters), full weight/filter inspection, per-channel ablation studies (zero out one conv filter, observe effect on steering output), and activation-patching between two recorded laps are all tractable "white-box" techniques — more feasible here than on typical large vision models, and arguably underused for DeepRacer.

**Bottom line on libraries**: because this tool holds a raw TF1 `Session`/`GraphDef` (not a `tf.keras.Model`), **none of the turnkey TF libraries (tf-keras-vis, tf-explain, Xplique) attach without first wrapping the graph** — e.g., writing a small adapter that exposes `__call__`/`predict` and, where needed, gradient tensors. Given that constraint, the most pragmatic next steps are (a) extending the existing hand-rolled gradient-based `GradCam` class with **HiResCAM/XGrad-CAM/Grad-CAM++** reweighting (minimal code delta, no new dependency), and (b) adding **gradient-free, forward-pass-only** methods (Occlusion, RISE, Score-CAM, Ablation-CAM, Recipro-CAM, Greydanus-style perturbation saliency) that only need repeated `session.run` calls and no autograd plumbing at all.

## DeepRacer-specific explainability landscape

No dedicated academic papers specifically on DeepRacer saliency/XAI were found. The practical landscape is almost entirely this tool's own lineage: `jochem725/deepracer-viz` (the original Grad-CAM-over-video tool, same README/approach now maintained as `larsll/deepracer-viz`) and generic community analysis tools (`aws-deepracer-community/deepracer-log-guru`, `deepracer-analysis`, `sasasavic82/deepracer-reward`, etc.) that focus on reward/lap-time/race-line analytics rather than model-internals visualization. No AWS blog post or published paper was found specifically proposing CAM variants, perturbation saliency, or XRL methods for DeepRacer — this appears to be a genuinely underexplored niche, and the existing Grad-CAM tool is, as far as this search could determine, the most advanced public DeepRacer-specific visual-explainability artifact.

## Top recommendations for the DeepRacer CLI viz tool

1. **Fix the faithfulness gap first, cheaply**: swap the current gradient-averaging step in `cam.py` for **HiResCAM**'s element-wise grad×activation (arXiv:2011.08891) — a few-line change with a proven faithfulness argument over vanilla Grad-CAM.
2. **Add one gradient-free sanity method with no new ML dependency**: implement **Occlusion** (sliding gray patch + `session.run`) or **Greydanus-style Gaussian-blur perturbation saliency** (arXiv:1711.00138) as a second overlay mode — both work purely via repeated forward passes on the existing frozen graph, serve as a faithfulness cross-check against the gradient-based map, and directly support continuous (SAC) outputs.
3. **Add XGrad-CAM and Grad-CAM++ as selectable `--method` flags** — minimal incremental code on top of the existing `tf.gradients` call, giving users a faithfulness/robustness vs. detail trade-off.
4. **Support action-specific explanations properly**: resolve the `TODO` in `cam.py` (hardcoded output index 0) to accept an arbitrary discrete action index or the continuous mean output, and consider **SARFA** (arXiv:1912.12191) or **Finer-CAM** (arXiv:2501.11309) for genuinely distinguishing *why this steering bin and not the visually similar neighboring bin* — the core discrete-action ambiguity in DeepRacer's small action spaces.
5. **Add lightweight non-saliency diagnostics**: per-frame policy entropy/value plotted over track position, and a t-SNE/UMAP of the penultimate dense layer colored by action — cheap (no new heavy dependency beyond scikit-learn/umap-learn), and complements saliency per the Atrey et al. critique (arXiv:1912.05743) that saliency alone should not be taken as ground-truth explanation.
6. **Wrap a minimal Quantus-compatible callable** around `Model.session.run` to report deletion/insertion AUC or ROAD-style faithfulness scores for whichever CAM method is active, rather than trusting visual inspection alone (per Adebayo et al., arXiv:1810.03292).
7. **Treat VisualBackProp (arXiv:1611.05418) as a strong low-cost alternative/complement**: it needs no gradients at all, was purpose-built for exactly this real-time small-steering-CNN use case, and could be added as a near-zero-dependency alternate explanation mode.
